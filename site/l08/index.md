# L08 · 多智能体系统

> 对应讲义 lecture08Multi-Agent Systems.pdf · p.3–89 · 约 50 分钟 · 前置：L01–L07 · **八讲收官**

最后一讲，复杂度光谱的顶端：**一群 agent 如何一起干活**。先泼冷水定调（讲义 p.13–14 的反直觉开场）：**有时单 agent 更好**——2026 年的实证研究（Kim et al.）发现不少任务上 SAS 胜过 MAS；讲义的建议是工程界的金句：**"先建强单 agent 基线；加 agent 要有明确目的，并测量收益是否盖过协调成本。"** 带着这个怀疑精神进入正题。

## 开场：MAS 的收益与代价账本

MAS = 多个 agent 面向共享任务的集合（p.10），设计要过三关：**编排**（谁指挥谁）、**通信**（怎么交换信息）、**协调**（怎么管相互依赖的工作）。

| 收益（p.11） | 代价（p.12） |
|---|---|
| **并行执行**：可分的子任务同时干 | **协调开销**：委派、消息、集成，吃时间吃 token |
| **专业化**：指令/模型/工具按角色定制 | **信息丢失**：交接时漏掉对方需要的上下文 |
| **聚焦上下文**：每个 agent 只看相关的 | **冲突动作**：重复劳动、互相覆写 |
| **更广探索**：多假设、多路径并进 | **误差传播 + 工程复杂度**：一个错带偏全队，调试面翻倍 |

**何时用哪个**（p.14 原表）：SAS——步骤强依赖、共享状态紧耦合、单 agent 已达标；MAS——子任务可少同步推进、信息可切分成聚焦上下文、能各自负责并集成、并行/专业化/独立评审**解决的是被测量过的瓶颈**。

补充两个要点：**架构取决于任务**（p.23——可分性、耦合度决定拓扑），以及**动态组队**是活跃方向。

**DyLAN 的四步组队法**（p.25–28，费曼级）：
1. **前向跑一遍**：把候选 agent 团队放出去，每人回答同一个问题——收集全部回答
2. **互相打分**：每个 agent 给其他人的回答评效用分（Utility Score，0-1）——同伴评估取代人工标注
3. **信用回传**：找到团队达成一致的答案 → 沿"谁贡献了这个答案"的链路回传信用分——贡献高的 agent 获得高 Agent Importance Score
4. **选队**：新任务来了，只带 Importance Score 高的精锐上——裁掉混子

**早停条件**：2/3 的 agent 给出一致答案即停——更多轮未必更好、还更贵。决策类任务上以更少的 API 调用拿到更高成功率——因为砍掉了"人浮于事"的 agent（从众效应的解法之一：只留有多样性的高贡献者）。

## 第二幕：通信——对话、交接与协议

先分清两个常被混用的词（p.31）：**通信 = 信息怎么交换**（谁收什么、走什么通道）；**协调 = 相互依赖的活怎么管**（谁拥有哪个任务、先后与冲突）。

**AutoGen 的世界观：多 agent 通信 = 对话**（p.32–35）。可定制每个 agent 并组织成对话模式：顺序交接、嵌套、群聊（共享上下文）、层级（都汇报给编排者）。

**Handoff vs Agent-as-Tool**（p.36–39）——L01 那一刀的多智能体版：

- **Handoff（交接）**：**控制权转移**——接收方成为活动 agent、直面用户、接管后续；上下文跟随。适合"专家该亲自接手"的场景；
- **Agent-as-Tool（agent 当工具）**：**调用方保留控制**——发一个有边界的请求 + 挑过的上下文，拿回结论继续自己干。适合"我主导、专家只出意见"。

**消息板**（p.40–44）：MetaGPT 用共享消息板协调；MoltBook 干脆做成"agent 的社交媒体"；**HuggingFace 事件**（p.43）提醒你：公开消息板 = 公开攻击面。

**A2A 协议**（p.45–48）：Google 的 Agent2Agent——**MCP 解决 agent↔工具，A2A 解决 agent↔agent**：Agent Card 描述远端 agent 的能力（发现），任务可追踪、可推送通知、来回消息、交付工件。跨组织 agent 生态的标准化正在铺轨。

## 第三幕：协调——基础设施与涌现模式

**基础设施三件套**（p.52–63）：

- **Task Ledger 任务账本**（Magentic-One）：编排者维护一本显式账——目标、计划、未决问题、分配、依赖、进度、阻塞；用它决策下一步、支撑恢复。**把"团队状态"从各 agent 的上下文里解放出来，变成共享工件**；
- **Symphony**（OpenAI）：把 **issue tracker 变成编排器**——监控 issue、把合格任务派给独立工作区的编码 agent（协调协议 = 现成的工单系统）；
- **G-Memory 共享记忆**（p.57–61）：为 MAS 定制的三层图记忆（洞察图/查询图/交互图）——**团队级记忆**打败了把单 agent 记忆设计直接搬过来的基线；
- **Worktree 隔离**：每个 agent 自己的 checkout + 分支，合并走受控集成——**执行期互不干扰，代价是集成工作**（分歧漂移）。

**涌现的协调模式**（CooperBench，p.64–67）：**角色分工**（谈好谁做哪块）、**资源分工**（切分共享资源防碰撞）、**谈判**（冲突方案收敛成一个计划）——agent 团队自己长出来的协作形状，与人类团队惊人地同构。

最响的两记警钟（p.73–81）：**协调的诅咒**——CooperBench 上"单 agent 做两份活"胜过"两 agent 协作"；**行为塌缩**——蜂群"独立创作"过半都造了光线追踪器（从众），以及目标不兼容时 agent 竟会"**以武力解决**"（改掉对方的部署成果，Anthropic 多智能体研究的名场面）。

## 第五幕：案例——Carlini 的编译器蜂群（p.84–89）

一个去中心化无限循环蜂群造 C 编译器的真实工程样本：**互补的专家角色 + Git 任务夹（通信+共享记忆）+ worktree 隔离（各自分支）+ agent 自选任务**。六条经验值得整段抄录：

1. **强测试引导自主工作**——正确性/回归测试让 agent 认得进度、抓得住破坏；
2. **为并行而设计**——暴露可分的失败面与子任务；
3. **协调显式化**——认领任务、独立克隆、经 Git 集成；
4. **跨会话保存知识**——共享文档、进度笔记、失败尝试记录（L07 的团队版）；
5. **反馈要高效**——精炼错误摘要、可搜索日志、快速测试子集；
6. **给互补的目标**——职责不同才不打架。

### 复刻清单 · 最小 MAS 零件

角色分工（谁做什么）→ 通信通道（消息板/交接/A2A）→ 共享账本（Task Ledger：目标/分配/依赖/进度）→ 隔离（worktree：互不踩脚）→ 冲突规则（谁说了算）。**缺账本 = 承诺失忆；缺隔离 = 互相覆写。**

## 带走三句话（也是八讲的收官）

1. MAS 的判据：**协调成本是真实价格**——先建强单 agent 基线，为被测量过的瓶颈而拆分；紧耦合的任务，一个脑子更好。
2. 三关各有工具：**编排**四拓扑（独立/中心/蜂群/混合，成本递增）、**通信**看控制权（Handoff 转移 vs Agent-as-Tool 保留——L01 的刀）、**协调**靠显式化工件（Task Ledger/共享记忆/worktree）。
3. 失败三族（一般性/协调/行为）里最深的教训是行为性的：**多样性是 MAS 的核心资产，从众与武力是它的两面深渊**。

> **八讲之旅到此闭环**：L01 你认识了"循环 + 通用大脑"和那把控制流的刀；L02 拆开大脑的物理性质；L03–L04 装上外挂器官（检索与工具）；L05–L06 学会选型与模式；L07 给它记忆；L08 把它组建成社会。贯穿始终的只有一条线——**给概率大脑加确定性边界，并在 pⁿ 的世界里把工程做可靠**。

## 思考题

<details>
  <summary>1 · 你的任务"两小时数据处理管道，步骤强依赖上一步输出"——MAS 吗？把判据说全。</summary>
  <p><b>参考答案</b>：不是。步骤强依赖 + 共享状态紧耦合是 SAS 的明确信号（p.14 左列）。MAS 的前提是"子任务可少同步推进、信息可切分、贡献可独立集成"。这个场景该做的是把每步做强（校验/重试/持久化——L05 Temporal），而不是加 agent。</p>
</details>

<details>
  <summary>2 · Handoff 与 Agent-as-Tool，哪个保留了调用方的控制权？这如何映射 L01 的判据？</summary>
  <p><b>参考答案</b>：Agent-as-Tool 保留（专家只是被调用的动作）；Handoff 转移（控制流交给了接手者）。映射：这仍是"谁决定下一步"——只不过决策对象从"模型 vs 代码"扩展成"agent A vs agent B"。工程含义：交接处是信息丢失的高发地（失败动物园的 inter-agent 失配），能当工具就别轻易交接。</p>
</details>

<details>
  <summary>3 · Task Ledger 治的是 pⁿ 的哪一种并发症？</summary>
  <p><b>参考答案</b>：上下文漂移导致的"承诺失信/期望错位"——每个 agent 只见自己窗口，团队状态没有共同事实源。账本把目标/分配/依赖/进度变成共享工件（外置的确定性状态），相当于给团队装了一个"共享工作记忆 + 单一事实源"。它是协调版的重试/校验闸：不提升单步智力，但防止错误在 agent 间复利。</p>
</details>

<details>
  <summary>4 · 设计一个三人 agent 团队做"技术调研报告"，给出拓扑、通信与协调的选择及理由。</summary>
  <p><b>参考答案（示例）</b>：拓扑=中心式（编排者拆题派活、集成成稿——报告需要统一叙事，蜂群必打架）；通信=Agent-as-Tool（检索员/分析员/撰稿员是专家工具，控制权留在编排者——避免交接失真）；协调=Task Ledger + 共享提纲文档（分工与依赖显式；L07 的共享记忆存"已核实事实"防重复劳动）。互补目标：一个查信源、一个做批判性评审——刻意制造多样性。</p>
</details>
