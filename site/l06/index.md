# L06 · 设计模式与脚手架

> 对应讲义 lecture06Agent Design Patterns and Scaffolds.pdf · p.3–86 · 约 50 分钟 · 前置：L05 · **配套实验：[Lab 01 第 6 步](/labs/)（最小 ReAct 闭环）**

L05 教你看穿框架；这一讲给你框架之下真正的复用资产——**被实践验证过的"循环形状"**。Martin Fowler 的开场白（p.4）定调：**"模式是半成品——你总要自己把它烤熟。"**

::: info 演进谱系 · 本讲的一条链
CoT（会想，但黑箱幻觉）→ ReAct（边想边做，接地）→ Reflexion（失败反思——但自评会错，反思必须来自外部信号）→ CodeAct（代码即动作）→ ReWOO（先规划后执行，把不确定性集中）。问题演进：**推理与行动的边界怎么划**。（[全课程谱系图 →](/lineage/)）
:::

## 开场：模式为什么存在

复习 L01–L05 的坐标（p.9–12）：**workflow 控制流在代码（可预测），agent 控制流在模型（自适应）**；真实系统是两者的混搭。于是两类设计模式自然分层：**工作流模式**（在代码侧组合模型调用）与 **agent 模式**（在模型侧设计推理与上下文）。

两个组合的真实样本（p.22–29）：

- **STORM**（写维基级长文）：一次用齐提示链（大纲→撰写）+ 并行化（多视角提问）+ 编排者-工人（派检索工人）+ 近似的评估者-优化者（事实核查循环）；
- **Archon**：更进一步做**架构搜索**——把"用哪些推理时技术、怎么组合"本身当成优化问题（连回 L05 的 DSPy Optimizer 思想）。

## 第二幕：推理与行动的四个模式

**ReAct（2023，p.33–36）**：核心洞见一句话——**行动之前先推理**。你已在 L01 剧场与[论文精读](/l01/readings/react/)里完整走过它；这里补讲义的历史注脚：原论文发现**要微调才有最佳表现**——如今"后训练出 agent 能力"已是各大模型的标配（L02 训练管道的终点）。

**Reflexion（2023，p.37–41）**：核心洞见——**把评估/反思变成 actor 的"记忆"（上下文）**。失败轨迹 → 自然语言反思 → 写进上下文 → 下一轮更聪明；跨尝试提升准确率，且实验证明**起作用的是反思文本，不是简单堆叠历史轨迹**。

但有个关键限定（p.41，*Large Language Models Cannot Self-Correct Reasoning Yet*）：**让 LLM 评估自己的回答会降低性能**——Reflexion 绕开它靠的是**外部环境反馈**（测试结果、执行信号）。推论出两条工程路线：**CRITIC（2024）**——把外部工具接给验证者，做一个"agentic verifier"；以及今天的路线——自省被内化进 reasoning 模型的训练里（L02 的推理预算）。

**CodeAct（2024，p.43–46）**：核心洞见——**代码是动作的正确形态**。同一道跨国比价题：JSON 动作要一轮轮"调工具→看结果→再调"；代码动作直接写一段程序，循环、变量、逻辑组合全用上——**成功率更高、轮数更少**。lab01 的中心命题在此升级：结构化输出面对的是"一次调用"，而**代码是能表达整个控制流的形式语言**——模型写代码时，它同时在做 orchestration。

**规划后执行（ReWOO / LLMCompiler，p.47–52）**：ReWOO 的洞见——**先规划全部步骤再执行，把 agent 的执行变回 workflow**：准确率更高、token 更少（因为不用把每个观察都喂回模型）。LLMCompiler 再加**并行执行 + 动态重规划**。方向感很重要：这不是否定 agent，而是说**不确定性应该集中在规划步**——规划之后，执行是确定性的（可并行、可缓存、可重试）。L01 那一刀在时间维度上的应用：**先让模型决定控制流（规划），再用代码执行控制流**。

## 第三幕：上下文管理的五个模式

两大原则（p.59）：**聚焦上下文**（只留当下需要的）与**保持连续性**（保住目标/约束/进度——实践上还包括保住 KV Cache，L02 的 append-only 铁律）。

## 第四幕：案例 Pi——极简主义的完整答案

讲义 p.76–83 把 L05 提过的 Pi 拆给你看，作为"设计模式如何落地"的标本：

- **哲学**："让 Pi 适配你的工作流，而不是反过来"——无子 agent、无权限弹窗、无 plan 模式、无 todo 列表，社区在它上面长出一切扩展；
- **工具**：只有 read / write / edit / bash——讲义原话：**"所有其他工具都是 bash 的子集"**（这也是 L02"避膨胀"的极致版）；
- **循环**：ReAct 式（推理先于行动），JSON 工具调用；上下文建为**树**，可回到早前分支另开一线；
- **上下文三板斧**：事件日志 → LLM 输入转换 + 技能文件的渐进披露 + 压缩——正好把本讲第三幕的三个模式各用一个；
- **安全**：以进程权限运行、无任何确认弹窗——**"视为永远在自动模式、无保护"**（L01 第四幕的安全课，这里是它的反面教材级注脚）。

## 带走三句话

1. 工作流五模式（链/路由/并行/编排-工人/评估-优化）是**代码侧的组合语法**；真实系统是它们的复合——模式是半成品，烤熟靠你的场景。
2. 推理与行动四模式各有一句灵魂：**先推理**（ReAct）、**反思来自外部信号**（Reflexion/CRITIC）、**代码是动作的终极形态**（CodeAct）、**把不确定性集中到规划步**（ReWOO/LLMCompiler）。
3. 上下文两原则（聚焦 + 连续）统领五模式（事件日志/卸载/压缩/遮蔽/隔离），**组合使用**；Pi 证明：极简 harness + 这套模式 = 生产级 agent。

## 思考题

<details>
  <summary>1 · 设计一个"客服工单系统"：至少组合三个工作流模式，说明各自位置。</summary>
  <p><b>参考答案（示例）</b>：<b>路由</b>开头（分类：退款咨询/技术故障/闲聊，不同类别不同模型与提示）→ 简单类别走<b>提示链</b>（检索政策→草拟回复→语气润色）；复杂类别进 <b>编排者-工人</b>（编排者拆出查订单、查物流、查历史工单，派工人并行调查后汇总）→ 高价值操作前挂<b>评估者-优化者</b>（合规检查循环）。外加一条底线：退款执行本身是纯代码 workflow，不交给模型。</p>
</details>

<details>
  <summary>2 · 为什么 Reflexion 必须依赖外部反馈，而今天的 reasoning 模型又能"自我修正"了？矛盾吗？</summary>
  <p><b>参考答案</b>：不矛盾。Reflexion 时代的模型若在<b>推理时</b>给自己打分，会把错误答案越改越错（自评偏差）；外部信号（测试/执行）是可判定的。今天 reasoning 模型的"自我修正"是<b>训练出来的</b>——RLVR 把"回检查再答"练进了权重（L02），本质仍是外部可验证奖励的内化。工程含义没变：部署时的关键决策仍要挂可判定信号，不能指望模型自评。</p>
</details>

<details>
  <summary>3 · CodeAct 与 lab01 的结构化输出是什么关系？</summary>
  <p><b>参考答案</b>：同一根问题的两级答案。结构化输出解决"一次调用的形态约束"（语法可判定）；CodeAct 把形态升级为<b>代码</b>——不仅能约束一次输出，还能表达循环/分支/变量，即一整段控制流。安全代价同步升级：结构化输出要校验闸，代码动作要沙箱（确定性边界随能力一起长大）。</p>
</details>

<details>
  <summary>4 · ReWOO 说"规划后执行更省 token"，代价是什么？什么时候它会输给 ReAct？</summary>
  <p><b>参考答案</b>：代价是<b>计划可能基于错误假设</b>——没有观察喂回来，规划时模型只能靠内部知识猜子任务；一旦执行中发现前提错了，要么全盘重来（ReWOO 的重规划较重）、要么带伤执行。当任务高度依赖中间观察（探索式 debugging、开放域检索）时，交错式的 ReAct 更稳——又回到 L01 判据：下一步依赖观察内容 → 交给模型边看边定。</p>
</details>
